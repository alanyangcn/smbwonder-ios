# 主机游戏原生移植方法论——以《超级马里奥 惊奇》Switch → iOS 为例

这份文档总结本项目从零开始，把 Switch 版《超级马里奥 惊奇》1.2.0 移植到 iPhone 并做到可玩的全过程：走过哪些阶段、遇到哪些难点、分别怎么定位和解决、哪些做法事后证明有效或无效。目的是让以后移植别的游戏、或移植到别的平台时，有一套可以照着走的思路，而不是只留下一堆零散记录。

逐轮的细节和证据在 [STATUS.md](../STATUS.md) 与 `work/analysis/first-frame/ledger.md`，本文只提炼方法和教训。文中 `main+0x…`、`sdk+0x…` 是游戏主程序和 SDK 模块里的代码偏移，`roundNNN` 是第几轮真机验证。

## 1. 总体路线：为什么是"原生执行 + 高层替换"

### 1.1 三种可能的路线

| 路线 | 做法 | 在 iOS 上的问题 |
|---|---|---|
| 完整模拟器 | 解释或 JIT 执行客体 CPU，模拟 GPU 硬件寄存器 | iOS 不允许普通 App 做 JIT；纯解释太慢；GPU 硬件级模拟工作量巨大 |
| 重写 / 反编译 | 把游戏逻辑反编译成源码重新编译 | 对现代 3D 游戏几乎不可行 |
| **原生执行 + 高层替换**（本项目） | 客体 AArch64 代码直接在 iPhone 的 ARM64 CPU 上跑；宿主接管系统调用、系统服务和图形 API | 需要解决代码签名、地址空间、ABI 差异；图形 API 要整套翻译 |

Switch 和 iPhone 都是 ARM64，所以游戏的机器码本身可以原样跑，真正要替换的只有三层：

1. **内核层**：客体执行 `svc` 指令进入 Horizon 内核（建线程、等事件、映射内存……），由宿主的 `sdk_kernel.c` / `kernel_threads.c` 实现。
2. **系统服务层**：SDK 里的服务客户端（音频、时间、文件、账号、设置……）会通过 `sm:` 连到系统进程。宿主不替换客户端，而是**只换掉"连接系统服务"那一层**（服务对象或平台函数），客户端逻辑照样原生执行。
3. **图形 API 层**：游戏调用 NVN（Switch 的图形 API），宿主实现全部用到的 NVN 函数，录制命令后回放成 Metal。着色器离线翻译成 MSL。

### 1.2 为什么替换"高层"而不是"低层"

- **越往上替换，要模拟的语义越少**。在 NVN API 这一层替换，就不用关心 Maxwell GPU 的寄存器和命令包格式。
- **代价是每个被替换的接口都必须精确符合原语义**，因为游戏的其余部分依然原生运行、完全信任这些接口。后文很多难点（命令内存大小、对象布局、时间戳语义）都源于这一点。
- 能留给原生代码做的，一律留给原生代码：音频用 SDK 自带的进程内 DSP 服务端；ngc（敏感词过滤）只换服务对象；SDK 自己的虚拟内存管理、堆、libc 都原生跑。

### 1.3 借鉴已有项目，但不照搬

本项目起点是同作者另一个移植（D2R Mobile）的装载器、改写工具、NVN→Metal 框架和翻译器。复用时坚持一条：**通用机制可以复用，游戏专用的地址、表格、结构一律不沿用**。早期审查就列出了参考代码里写死的游戏 ID、固定地址、空实现的 NVN 函数、按另一款游戏手工维护的着色器表，逐个替换（见 [PORTING.md](../PORTING.md) 的改造点表）。

## 2. 贯穿始终的工作原则

这些原则写在 [CLAUDE.md](../CLAUDE.md) 里，是整个项目能稳定推进的根本。

### 2.1 不跳过、不伪造，遇到不支持就"按名停止"

- 缺一个接口、遇到一个不支持的参数，就调用 `die(...)` / `wonder_nvn_stop(...)` 停下，**日志里写明函数名、参数和调用位置**。
- 绝不返回"假成功"、绝不画假帧。返回假成功会让游戏带着错误状态继续跑，几百帧后在完全无关的地方崩溃，比停在原地难查十倍。
- 好处：每一轮真机运行都会精确停在"下一个缺口"，项目进度就是一条"停点 → 实现 → 下一个停点"的链。

> 例外要有依据并写明：例如采集模式下缺着色器只跳过那次绘制（第 3.6 节），未绑定的只读存储槽读零（与 Switch 硬件行为一致）。凡是这种"不停"的处理，都要能说清"Switch 上就是这样"。

### 2.2 每个结论落到证据上

- 语义从哪来：**SDK 反汇编**（目标 SDK 的真实实现）、**游戏代码反汇编**（实际调用方式）、**RomFS 统计**（真实数据里出现过哪些取值）、**参考实现**（Ryujinx/yuzu 等模拟器对同一硬件行为的处理）。
- 结论写进代码注释和 ledger 时带上偏移（如"按 sdk+0x442d00 只记录"）和轮次号，以后回头查有据可依。
- 有一次本项目用 unicorn 直接跑 SDK 自带的 NVN 驱动代码当"真值"，逐项核对贴图大小/对齐（304 种描述全部一致），这类"用原厂代码当裁判"的方法非常可靠。

### 2.3 每轮闭环

1. 跑一轮真机 → 读停点 → 符号化调用栈 → 用反汇编确认真实语义；
2. 实现 → 补测试 → 全部宿主测试通过；
3. 更新 STATUS 和 ledger；
4. 每个大步骤提交一次。

### 2.4 可单测的逻辑独立成文件

不依赖宿主装载器的逻辑（存档事务、敏感词服务对象、命令记录存储、帧率统计、待定写入表……）放进独立 C 文件，配 C 测试 + Python 包装，在 Mac 上跑。真机一轮要几分钟，宿主测试几十秒，能在宿主测掉的问题绝不留到真机。

### 2.5 改动要可开关

性能和语义上有风险的改动都带环境变量开关（如 `WONDER_ASYNC_SUBMIT=0`、`WONDER_FAST_CONDITIONAL=0`、`WONDER_TBDR=0`、`WONDER_COMMIT_DRAWS=0`），出问题时不用重新构建就能对照。诊断功能同理（`WONDER_NVN_TRACE`、`WONDER_DRAW_LOG`、`WONDER_TEX_DUMP_FS`……）。

## 3. 阶段流程：从拿到游戏包到可玩

整个项目大致按下面十个阶段推进。每个阶段写明目标、方法、通过条件和本项目踩过的坑。

### 3.0 输入与环境

**目标**：可重复地得到游戏的可执行模块和资源，并能在新机器上一键重建环境。

- 解包：NSZ → NSP → NCA，本体与更新合并（ExeFS 用更新的，RomFS 合并）。记录 Title ID、版本号（本项目 1.2.0 / update 262144）、每个文件的 SHA-256。
- `verified-inputs.json` 固定原始 NSO、改写后映像和工具链产物的哈希，**构建前逐项核对**，防止用错版本。
- 新机器三步：`tools/setup_env.sh`（工具链）→ `tools/import_game.sh`（游戏包 + 密钥，按哈希核对）→ `tools/local_state.sh import`（着色器普查等本地状态）。
- 游戏文件、密钥、工具链、构建产物、设备日志全部放在 `work/`，不进 Git。

**坑**：换了一台 Apple Silicon Mac（无 Rosetta）后，所有 x86 工具要按本机架构重装；用 arm64 工具链重建着色器后，要和原产物逐字节对比，确认结果一致。

### 3.1 静态盘点

**目标**：开始写代码前，先知道"游戏到底用了什么"。

- 模块：main、sdk 各自的段、动态符号、重定位类型和数量、导入表。
- 系统调用：哪些 SVC、哪些服务（按导入的 `nn::xxx` 名字统计）。
- 图形 API：游戏实际引用了多少个 NVN 函数。
- 资源格式：着色器容器（BNSH / BFSHA / sharcb）、贴图（BNTX）、配置（BYML）、文本（MSBT）。

**坑：引用扫描漏统计**。最初只统计了 `adrp+ldr` 形式的函数槽读取，漏了 `adrp+add` 和尾调用 `br`，以为缺的函数很少，实际缺 100 个（共引用 241 个）。**盘点工具要覆盖编译器所有可能的取址方式**，最好用"全部字节扫描 + 排除已知区域"的办法交叉验证。

**有用的发现**：SDK 自带一份 NVN 名字表 → 偏移表 → 派发槽 → 实现表，可以按名字直接找到每个 NVN 函数在 SDK 里的真实实现，逐个核对语义。找"原厂真值"值得花时间。

### 3.2 CPU 层：让客体代码能在 iOS 上执行

**目标**：游戏模块被装载、重定位、签名后能在 iPhone 上执行第一条指令。

- iOS 不允许运行时生成或修改可执行代码，客体代码必须**离线改写后随 App 一起签名**。改写只处理必须拦截的指令点（系统调用入口等），并有结构检查 + 等价检查（本项目 3.4 万个站点、600 个变异样本全部检出）。
- 装载器按白名单处理重定位类型，遇到未知类型就停，不默默跳过。
- 恢复原来的模块相对布局，重定位只写数据段。

**坑：被系统拦截的指令**。SDK 里有 3 处读 `CTR_EL0` 寄存器（缓存行大小），iOS 直接报非法指令。处理办法：主要入口（`os::FlushDataCache`）通过 PLT 强制换成宿主实现，其余位置在 SIGILL 处理器里精确模拟这条指令。注意：调试器附加时这类陷阱会被当成崩溃，所以不能把陷阱当主路径。

### 3.3 引导：线程、内存、SDK 初始化、进入游戏入口

**目标**：SDK 初始化完成，模块构造函数执行，进入 `nnMain`。

- 线程环境要按**目标 SDK 的真实布局**来做（TLS 指针、线程对象在 TLR 的哪个偏移），不能沿用参考项目的结构。
- 主线程栈按 NPDM 里写的大小精确分配（本项目 1 MiB），并在真机上断言实际大小。
- 每次进程启动写唯一 run ID、debugger 状态，区分"调试器启动"和"独立冷启动"两种验证。
- 未知 SVC 一律终止客体线程并报 `BOOT_BLOCKED`，内核调用是一个个按停点补出来的：优先级、核心掩码、传输内存、地址区域、事件……

**坑：地址空间太小**。换场景时游戏闪退，根因是 alias 区只剩约 40 MiB，SDK 的虚拟地址管理为远景模型申请地址区失败（返回 0x1803），游戏没检查就用空指针。把 alias 区改成占满剩余地址空间（5376 MiB）后解决。**Switch 游戏默认拥有很大的地址空间，宿主给的地址区域要足够大**，必要时申请 iOS 的扩展虚拟地址权限。

### 3.4 系统服务：做一台"离线 Switch"

**目标**：游戏启动路径上的每个系统服务都有宿主实现或原生实现。

策略是**离线主机**：单个本地用户、无网络、不上传报告。每个服务按"游戏实际调用到的接口"逐个实现：

| 服务 | 做法 |
|---|---|
| 音频 | 用 SDK 自带的进程内 DSP 服务端；宿主只补平台层（DSP 帧节拍、设备查询），并把最终混音从 DeviceSink 取出送到 iOS 的 RemoteIO |
| 时间 | 按 iOS 系统时钟和时区实现 14 个接口 |
| OE（应用环境） | 显示版本取自游戏的 control.nacp，伪设备 ID 持久化，焦点/运行模式跟随 iOS 生命周期 |
| 文件 / RomFS | 只读资源归档 + 宿主存档；存档做成"工作副本 + 原子提交"，中断可恢复 |
| 好友 / 网络 / DLC | 按离线语义返回（空列表、网络不可用、DLC 数 0） |
| 敏感词过滤、设置 | 客户端原生，只把背后的服务对象换成宿主对象（按 SDK 的虚表顺序实现） |

**几个通用经验**：

- **"纯函数"不一定纯**：`settings::operator==(Language, LanguageCode)` 看似比较两个值，实际内部会连系统服务查可用语言列表。要以反汇编为准，不要以名字猜。
- **进程内事件不跨进程**：音频服务端创建的系统事件是进程本地的，游戏拿到的句柄是 0。宿主要把它换成真实的内核事件，并在每帧 DSP 结束后发信号。
- **原本由别的系统模块做的事要补上**：SDK 进程内版本里，没人创建音频系统管理器，也没人调用 Add（那是系统音频模块的职责），宿主要代劳。
- **路径规范化**：音频引擎请求 `content://Sound/Resource/Stream/*.bwav`（双斜杠），真实 nn::fs 会合并连续分隔符，宿主 RomFS 没有，导致所有流式音频打不开，进而让一个声音联动对象为空，换场景时崩溃。**文件系统的容错行为也是语义的一部分**。
- **小栈陷阱**：客体线程的栈可能很小，宿主代码在客体栈上开 64 KiB 缓冲会溢出（存档首次提交时崩溃），宿主的大缓冲要放堆上或放到专用宿主线程。Metal 编译着色器也要离开客体小栈。

### 3.5 图形 API：NVN 对象与命令

**目标**：游戏的全部 NVN 调用都有实现，命令能录制、提交、回放到 Metal。

- **对象布局必须按目标 SDK**：命令缓冲对象是 0xa0 字节，游戏会直接读写其中某些字段（+0x10 的标志、+0x20/+0x28 的控制段指针），宿主自己的数据只能放在游戏不碰的位置或外部注册表。纹理视图是 16 字节而不是参考项目的 40 字节，弄错就会覆盖相邻变量。
- **调用顺序要宽容**：SDK 允许先 SetDevice 再 SetDefaults，宿主不能要求反过来。以游戏真实调用顺序和 SDK 实现为准。
- **命令录制放在宿主**：游戏会按 `GetCommandMemoryUsed` 的结果精确给每个模型预留 GPU 内存（详见案例 6.1）。宿主在客体命令内存里只写 8 字节引用，真正的命令记录放宿主表里。
- **调用另一个命令缓冲时要快照**：NVN 的 CallCommands 本来就会把被调用的控制项拷进调用方。宿主如果只记句柄、回放时再去读，游戏线程可能已经为下一帧重录了同一块内存（案例 6.2）。
- **资源按存储位置识别**：游戏每帧在同一块内存池偏移上重建临时渲染目标，宿主若按对象识别，每个新对象都拿到一张未初始化的 Metal 纹理（案例 6.3）。

### 3.6 着色器：离线翻译 + 普查循环

这是整个图形层工作量最大的部分。

**链路**：Maxwell 着色器二进制 → 翻译器（Ryujinx 着色器前端的定制副本，输出 SPIR-V）→ spirv-cross → MSL 3.2，同时生成一份行格式的反射文件（`.refl`：常量缓冲、贴图、采样器、存储缓冲、顶点属性、输出类型等的绑定位置）。设备上用 `newLibraryWithSource` 编译并按键缓存。

**翻译器需要回答的问题**（贴图维度、图像格式、顶点属性类型、输出类型、线程组大小）**全部来自真实数据，不允许默认值**：

1. **普查（census）**：游戏第一次用到某个程序时，宿主把当时的完整绘制状态（绑定的贴图描述、属性格式、渲染目标格式……）和着色器字节写到 `Documents/DrawCensus/`。
2. **离线全量提取**：从 RomFS 的所有着色器容器里取出全部程序（本项目最终约 1.1 万个阶段）。离线没有绑定信息的部分先按指令推断（如按 2D），**宿主在每次绘制时核对实际绑定**，不符就按名停止或记普查。
3. **采集模式**（`WONDER_CENSUS_SWEEP=1`）：缺着色器或类型不符时，只记普查、跳过这次绘制，游戏继续跑，一次运行就能收集沿途全部缺口。之后重建，再装正式版。

**着色器键必须覆盖全部影响结果的字节**（案例 6.7）。本项目一度只用控制段算键，1395 个控制段被不同代码共用，导致前景大片变蓝。

**翻译器本身的坑**：Ryujinx 的 AST 优化器会把间接跳转（BRX）只保留一个目标，导致文字顶点着色器取错 UV、文字全部不显示（案例 6.4）。改为全部阶段用 DebugMode 翻译。**翻译器是"别人的代码"，它的优化和默认值都要怀疑**。

**需要宿主精确实现的硬件语义**（每一条都对应一次真机停点或画面错误）：

- 常量缓冲越界读返回 0（Metal 会读到后面的内存或越界）；
- 顶点流越界读返回 0（流补零）；
- 未启用的顶点属性读 (0,0,0,1)；
- 深度模式 NEAR_IS_MINUS_W：顶点阶段输出 z' = (z + w) / 2；
- 无绑定贴图句柄从常量缓冲读，贴图句柄表在 `c[2][0x20 + 8r]`，常量缓冲 r 是 `c[3 + r]`（按 SDK 实测，参考项目的偏移是错的）；
- 2D 数组指令采样 2D 贴图读第 0 层、立方体声明遇到 2D 贴图读 0；
- 句柄 0 是"空槽"，读 0；
- 时间戳报告、条件渲染（见案例 6.9）。

**最终残留**：19 个阶段无法离线构建（16 个计算着色器缺图像格式，2 个读驱动常量 `c[0]+0x610`，1 个 spirv-cross 失败），全部来自引擎通用图形库，靠采集模式在遇到时自动记录。

### 3.7 iOS 外壳

- **生命周期**：iOS 27 强制 UIScene；横屏、全屏、隐藏状态栏和 Home 条。前后台切换要通知游戏焦点变化，并在后台关闭 GPU 提交（iOS 禁止后台 GPU 工作，否则命令缓冲直接报错）。
- **输入**：半透明触屏按键 + GameController 手柄，写入游戏读的手持手柄状态。支持脚本按键（`WONDER_AUTO_INPUT`），无人值守也能从标题走到关卡。
- **字体**：Switch 的共享字体在离线主机上没有。iOS 27 的苹方是 hvgl 可变字形格式（没有 glyf/CFF 轮廓），游戏的字体引擎读不了，要按候选列表找带传统轮廓的系统字体，重建成标准 SFNT。按键图标是任天堂扩展字体的私用区码位，统计游戏文本里实际用到的 27 个码位后自绘一套图标字体。
- **签名**：免费个人账号描述文件 7 天过期，而且拿不到"扩展虚拟内存"权限；付费账号一年，权限齐全。换账号意味着换包名、等于换一个 App，**存档和用户身份文件要手动迁移**（案例 6.13）。

### 3.8 可玩之后：性能

见第 7 节。

### 3.9 长尾稳定性

可玩之后，问题变成"玩到某个地方偶尔卡住"。这时最重要的是**让每次卡住都留下能直接定位的信息**：

- `Documents/last-stop.txt`：停止原因单独写一个小文件（主日志有大小上限，曾经因为日志被截断而丢失停止原因）。
- `Documents/missing-shaders.txt`：每个首次遇到的缺失程序，连同当时加载的关卡文件名。后来据此精确定位到"第 5 世界某关卡的某个子区域"。
- 地址错误时报出：回放到第几次提交、第几条命令、该地址曾属于哪个已释放的内存池、释放时游戏的调用链、距释放过了多少帧。案例 6.10 靠这些信息三轮就定位清楚。

### 3.10 游戏内容侧的逆向（可选）

本项目按玩家要求修改了存档（解锁世界、关卡、徽章），积累了一套"读懂游戏数据"的方法，见第 5.4 节。

## 4. 每一轮真机验证怎么做

### 4.1 一键轮次脚本

```sh
tools/device_round.sh first-frame-round<N>            # 测试 → 构建 → 签名 → 安装 → 启动 → 取日志
tools/census_round.sh <上一轮> <下一轮>                 # 取回普查 → 加入构建清单 → 重建着色器 → 启动下一轮
```

- 宿主测试不过就不构建；构建失败就不安装；**安装失败绝不自动卸载**（卸载会删掉 App 的 Documents，也就是存档）。
- 3.7 GB 的 RomFS 只传一次，按 SHA-256 标记，之后的轮次不重复传。
- 启动用 `xcrun devicectl device process launch --console`，App 的 stderr 实时写进 `console-*.log`。
- 交互模式（`WONDER_INTERACTIVE=1`）：App 启动后脚本退出，玩家继续玩，日志继续写，需要时再 `--fetch-only` 取回。
- 轮次名递增，不覆盖旧结果。

### 4.2 启动参数要随轮次一起保存

诊断和功能开关通过 `WONDER_ENVS` 传给 App，并写进 `Documents/launch-env.txt`，**从桌面图标启动时也生效**。教训：有几轮漏传了这个变量，空值覆盖了文件，采集模式被关掉，缺着色器从"少画一点"变成"卡住"，玩家看到连续几次卡死（第 8 节）。

### 4.3 一轮的标准动作

1. 读停点：`last-stop.txt` / `console-*.log` 里的 `BOOT_BLOCKED`、`NVN_BLOCKED`、`GUEST_FAULT`；
2. 符号化：`python3 tools/symbolize.py sdk+0x… main+0x…`，`--dis N` 反汇编（能解析 PLT 桩），`--find 文本` 查符号；
3. 读反汇编确认真实语义，必要时 LLDB 附加到正在运行的游戏取现场；
4. 实现 + 测试 + 记录 + 提交；
5. 下一轮。

## 5. 定位问题的手段清单

### 5.1 不重启地看运行中的游戏

- **LLDB 附加**正在运行的游戏进程：读寄存器、读内存、下断点、调用宿主诊断函数，看完分离，游戏继续跑。适合"只在某个场景出现"的问题。注意：模块查找失败时脚本可能误杀进程，脚本要先做存在性检查。
- **周期性采样客体线程**（`KERNEL_RUNNING`）：每 30 秒挂起未阻塞的线程、读 pc 和调用链、立刻恢复，定位"游戏在轮询什么条件"。
- **阻塞线程报告**（`KERNEL_WAIT`）：列出等待超过 5 秒的线程和等待起点调用栈。

### 5.2 画面问题

- **逐绘制日志**（`WONDER_DRAW_LOG`）：每次绘制的程序、清屏色、写掩码、混合、深度、剔除、绕向。案例 6.7 靠它发现"蓝色其实是游戏自己的清屏色"。
- **贴图与常量转储**（`WONDER_TEX_DUMP_FS`）：某个片元程序采样的每张贴图各级、透明通道、读到的常量和前几个顶点的原始数据。
- **逐程序画面 + 深度截图**（`WONDER_DRAW_DUMP`、`WONDER_FRAME_DUMP_EVERY`）。
- **诊断开关做对照实验**：对某些着色器关掉深度测试、关掉剔除、冻结时间戳……一次只改一个变量，看现象怎么变。案例 6.7 和 6.9 都是这样排除出来的。

### 5.3 性能问题

- **Time Profiler**（`xcrun xctrace record --attach <pid>`）：看各线程 CPU 热点。附加偶尔失败，重试即可；全进程模式下自己的 App 可能没有符号。
- **Metal System Trace**：看 GPU 各通道忙碌比例；导出编码器列表，按编码器标签归类 GPU 时间（"多绘制通道 / 单绘制通道 / 拷贝"），这是找 GPU 浪费的关键。
- **自建计时**（`HOST_FRAME_TIME`、`HOST_MEMORY`）：每 300 帧打印回放线程空闲、等 GPU 次数和耗时、等可用画面、GPU 实际时间、游戏线程等待同步对象的时间、渲染通道关闭原因、拷贝原因。**通用分析工具看不到"谁在等谁"，自建计时能**。

### 5.4 读懂游戏的数据和逻辑

- **字符串 → 代码**：在主程序里找字符串（如 `_Hidden`、`CanOpenWorldName`），扫描 `adrp+add` 找到引用它的代码，再反汇编看判断条件。
- **没有 RTTI 时找类**：从重定位表里找指向某函数的虚表槽，沿虚表往前找到虚表起点，再找写入这个虚表地址的构造函数。
- **名字哈希爆破**：存档里只有名字的 MurmurHash3。从主程序和 RomFS 所有文件里收集全部标识符字符串（约 66 万个），逐个算哈希比对；再用"结构名.成员名"组合（C 程序一分钟跑完）。GameDataList 的结构体定义里有"成员名哈希 → 字段哈希"的对应，比盲目组合更有效。
- **数据格式**：BYML（大端，v7）、MSBT（LBL1 标签 + TXT2 文本，UTF-16）、SARC、BNTX、sharcb（BAHS v9）都写了解析脚本；用中文文本库里的显示字符串（比如"？？？"）反查标签名，是从界面现象定位逻辑的好入口。
- **对比法**：多打几关、对比存档前后差异（`tools/save_diff.py`），摸清每个字段的含义。

## 6. 典型疑难问题案例

每个案例按"现象 → 定位 → 根因 → 解法 → 教训"整理。

### 6.1 模型静默缺失：宿主命令记录把精确定大小的堆撑爆（round125）

- **现象**：某个角色模型（耀西）的绘制用到空内存池。
- **定位**：LLDB 真机附加 + unicorn 跑 SDK 自带的 NVN 驱动做对照。
- **根因**：游戏用预录命令的 `GetCommandMemoryUsed` 结果给每个模型形状预留 GPU 内存，资源堆按 RSTB 精确定大小。宿主把命令完整内联写进客体命令内存（16 字节头 + 每个参数 8 字节），比真 NVN 的命令大，堆差几 KB，48 KiB 的块分配静默失败。
- **解法**：命令记录移到宿主表（`command_store.c`），客体命令内存每条只写 8 字节引用，不大于任何一条 NVN 命令。
- **教训**：**宿主在客体内存里留下的任何东西，大小都可能被游戏精确依赖**。

### 6.2 标题画面闪烁：命令句柄回放时才读（round97–108）

- **现象**：标题主视觉图和黑屏 / 蓝屏 / 斜切色块交替闪烁。
- **定位**：逐步排除（等 GPU 完成再取画面、同步提交、按存储识别纹理），最后记录调用时和回放时同一句柄的内容：录制时 2520 字节，回放时 9864 字节。
- **根因**：CallCommands 只记了句柄。游戏工作线程在本帧提交期间，就为下一帧重录了同一块控制内存，UI 层每帧被执行 0、1 或 2 次。
- **解法**：录制 CallCommands 时就快照被调用的命令段（真 NVN 本来就会把控制项拷进调用方）。
- **教训**：**"引用"和"拷贝"的语义差别，在多线程录制下会变成时序 bug**。

### 6.3 临时渲染目标拿到空纹理（round102）

- **现象**：同样的绘制序列，有时画出主视觉图，有时是黑的。
- **根因**：游戏每帧在同一池偏移上重建 9 张临时渲染目标，并读取上一帧画在那里的内容。宿主按纹理对象建 Metal 纹理，每个新对象都是空白。
- **解法**：GPU 写入的纹理按存储（内存池 + 偏移 + 布局）识别（`texture_storage.c`），覆盖同段内存的新纹理淘汰旧条目。
- **教训**：**在统一内存的主机上，"同一块内存"才是身份，对象只是视图**。

### 6.4 文字不显示：翻译器优化器丢分支（round138）

- **现象**：所有文字都不显示，贴图、采样器、混合都正常。
- **定位**：文字顶点着色器用两个间接跳转（BRX，跳转表各 3 个目标）按顶点角选 UV 字段；翻译结果里每个 BRX 只剩一个目标。
- **根因**：Ryujinx 的 AST 优化器的行为。
- **解法**：全部阶段用 DebugMode（跳过该优化器）翻译。
- **教训**：**翻译工具的优化和简化也要验证**；遇到"所有输入都对、输出不对"，要怀疑中间工具。

### 6.5 换场景闪退：远景模型从未加载（round141–146）

- **现象**：换场景时空指针崩溃，同时关卡远景一直是黑块。
- **定位**：崩溃点附近有声音联动对象的字符串；同期日志显示所有流式音频都打不开；远景模型文件在 RomFS 里，但游戏从没打开过。
- **根因**：两个独立问题叠在一起：（1）RomFS 不合并双斜杠，流式音频全部失败；（2）地址区域太小，虚拟内存管理为远景模型申请地址区失败（0x1803）。
- **解法**：RomFS 规范化路径；alias 区占满剩余地址空间。
- **教训**：**一个崩溃可能是两个根因叠加**；同一时期日志里所有"失败但没停"的记录都值得看。

### 6.6 关卡卡在 5 fps：每次绘制都对贴图算哈希（round141–143）

- **现象**：进关卡后只有约 5 fps。
- **根因**：为了发现 CPU 改写了贴图数据，每次绘制都对绑定的每张 CPU 贴图做整块哈希，每帧上百 MB。
- **解法**：页保护脏页跟踪（`page_guard.c`）：上传后把贴图所在页设为只读，CPU 写入触发异常 → 标脏 → 放开页 → 重试写入；宿主读文件写入这些页之前先放开。5 fps → 约 41 fps。
- **教训**：**"每次都检查"要换成"变了才通知"**，硬件内存保护是现成的变更通知机制。

### 6.7 关卡前景变成蓝色：着色器键撞车（round146–195）

这是本项目最难的一个画面问题，前后用了约 40 轮。

- **现象**：关卡前景的灌木、斜坡草、音符块所在区域显示成纯蓝色。
- **走过的弯路**：怀疑采样器上限、深度精度（EQUAL 改 LEQUAL 无效）、CPU/GPU 竞争（同步提交无效）、条件渲染（0 次跳过）、某个计算着色器……都排除了。还一度得出"游戏根本没录制颜色绘制"的错误结论（按顶点着色器名字没对上，实际颜色绘制用的是另一组变体）。
- **转折**：逐绘制日志显示，蓝色是游戏自己的清屏色；每个前景预通道网格都有同网格的颜色绘制，但一个像素都没写。对颜色着色器同时关深度和剔除，灌木出现；只关其一不出现，说明颜色绘制的几何和预通道不一致。再转储常量：两者顶点、常量完全相同，但翻译出的预通道着色器加的是 `-c4[8].y`，颜色着色器加的是 `+c4[8].x`，而原始 Maxwell 代码三处都是同一条 `FADD … c[0x4][0x80]`。**翻译结果不是这份代码**。
- **根因**：着色器键只取控制段的哈希。SecredUber 的 6494 个控制段里，1395 个被代码不同的阶段共用，于是这些阶段跑的是别的变体的代码。
- **解法**：键 = sha256(控制段 ‖ 代码)，宿主在设置程序时计算并随快照传递；离线工具从字节重算键，旧普查目录名里的旧键不再采信。
- **教训**：**缓存键必须覆盖全部影响结果的输入**；排查时"按名字对应"不可靠，要按内容（索引数、常量）对应；对照实验每次只改一个变量。

### 6.8 按键图标显示"?"：私用区字体（round196）

- **根因**：Switch 共享字体第 5 类是任天堂扩展字体，按键符号放在私用区，离线主机没有这份字体。
- **解法**：统计游戏全部语言文本里实际用到的私用区码位（27 个），按上下文推断含义，自绘一套图标字体打包进 App，缺失时按名停止。
- **教训**：**先统计"实际用到哪些"，再决定补多少**，不要试图复刻整份系统资源。

### 6.9 世界地图闪烁与帧率：时间戳语义（round199–220）

- **背景**：条件渲染（按 GPU 写入的报告值决定画不画）每次都要等 GPU 跑完，地图上每帧约 36 次，CPU 和 GPU 只能轮流干活。
- **第一次尝试**：做"快速判断"——跟踪尚未落地的 GPU 写入，能确定的就不等 GPU。校验显示每次判断都正确（0 次不一致），**但世界地图开始闪烁**。
- **定位**：统计发现剩下还需要等 GPU 的判断，读的全是时间戳记录。假设：游戏用时间戳测 GPU 耗时并据此调画质。诊断开关"冻结时间戳"（GPU 耗时恒为 0）打开后，闪烁消失，假设成立。
- **根因**：宿主在 GPU 完成时取 CPU 时钟当时间戳，测出来的"GPU 耗时"随每次等 GPU 剧烈跳变，游戏的画质来回切换。
- **解法**：照 Ryujinx / yuzu 的"快速 GPU 时间"：时间戳 = 回放到该命令时的时刻 ÷ 256。这样既平滑单调，在回放时又是已知值，条件判断全部不用再等 GPU。
- **副作用**：游戏以为 GPU 很快，把画质拉满（每帧约 870 → 990 个物件）。后续靠性能优化补回。
- **教训**：**校验"值正确"不等于语义正确**，要问"游戏拿这个值去做什么"。另外，模拟器社区对同一问题往往早有成熟方案，先去查。

### 6.10 偶发卡死：游戏用已释放内存池里的缓冲（round208–224）

- **现象**：玩一段时间后偶尔卡住，报某个地址不属于任何内存池。
- **定位**：分三步加信息。先报出回放位置；再报出"该地址曾属于哪个已释放的池、释放时的游戏调用链"；最后报出"距释放过了多少帧、多少次释放"。结论：世界地图某个对象的析构函数释放了 64 KiB 内存池，但游戏仍保留着池里的一个缓冲对象，**几千帧后**还在用它画东西。
- **为什么 Switch 上没事**：池释放后那块游戏内存仍然映射着，GPU 读到旧数据也不出错。
- **解法的演进**：保留 3 帧（不够）→ 600 帧（不够）→ 保留最近 64 个（不够）→ **记录最近 1024 个已释放池的地址范围，读到时当场重建零拷贝视图**。
- **教训**：**按时间设宽限期是在猜，要找到"什么条件下真的不会再被用"**；猜不到时就做成按需恢复。另外，每次失败都让报错多带一点信息，三轮内就能收敛。

### 6.11 未绑定的存储缓冲（round213–214）

- **现象**：一个片元着色器声明了存储缓冲槽 0，游戏却没绑定；之后一个计算着色器往未绑定的槽写数据。
- **解法**：只读时绑定 64 KiB 全零块（Maxwell 读空槽返回 0）；写入时绑定单独的丢弃块（模拟器的哑缓冲做法），写入不污染读零那块。
- **教训**：**"游戏没绑定"本身是合法状态**，要按硬件行为给出确定结果，而不是停下。

### 6.12 世界名显示"？？？"：从界面文字反查逻辑（round215）

- **方法**：在中文文本库里找"？？？"对应的标签（`WorldName_Hidden`）→ 在主程序里找拼接 `_Hidden` 的代码 → 反汇编看它判断的字段 → 从 AI/事件节点名找到两个相关事件（"到访过世界""王子告知世界名"）→ 从 GameDataList 的结构体定义找到对应字段 → 改存档。
- **教训**：**从玩家看到的现象（一段文字、一个图标）倒推，是逆向游戏逻辑最快的入口**。

### 6.13 签名、包名与存档迁移（round109、round230）

- **现象**：同一台手机在付费团队里"已注册"，安装却报"描述文件不能装在这台设备上"。
- **根因**：Xcode 缓存的描述文件生成于设备注册之前，不包含这台设备。
- **解法**：把旧描述文件移走，让 Xcode 重新生成。付费团队不能用个人团队注册过的包名，所以新 App 用新包名，存档和用户 ID 文件（`account/uid.bin`，存档按用户 ID 分目录）一起手动迁移并逐字节核对。
- **教训**：**包名就是 App 的身份**，换包名前先备份存档和身份文件。

### 6.14 发热降频（round235，已知未处理）

- **现象**：同一画面刚开始 60 fps，几十秒后掉到 45–50 fps。
- **定位**：每帧工作量不变，而 GPU 时间从约 10.7 ms 升到约 18 ms；Metal System Trace 记录的设备温度状态是 Serious。
- **结论**：手机发热，iOS 降低了 CPU/GPU 频率（测试时手机长时间连着 USB 充电满载）。
- **教训**：**性能测试要记录温度状态**，否则会把降频误判成自己的回退。

## 7. 性能优化方法论

### 7.1 先建立测量，再优化

1. 先确定瓶颈在哪一方：游戏线程、回放线程、GPU，还是它们在**互相等**。本项目有很长一段时间三方都只用了三四成，瓶颈全在"等"上，通用分析工具看不出来，靠自建的 `HOST_FRAME_TIME` 才看清。
2. 每次只改一处，改完在**同一场景**测；记录绘制数和渲染通道数，确认工作量可比（游戏会根据测得的性能调整画质，见案例 6.9）。
3. 区分"场景刚加载"和"稳定一段时间后"，后者可能已经降频（案例 6.14）。

### 7.2 本项目的优化时间线（最重的世界地图视角）

| 轮次 | 改动 | 效果 |
|---|---|---|
| r138 | 同一组渲染目标的连续绘制合并成一个渲染通道；拷贝集中到前置 blit | 关卡约 6 fps → 可玩 |
| r143 | 贴图改用页保护脏页跟踪，不再每次哈希 | 关卡 5 → 41 fps |
| r198–203 | 句柄表、内存池索引、程序表改哈希；常量缓冲、视图缓存 | 卡的关卡 11 → 22 fps |
| r220 | 时间戳改快速 GPU 时间，条件渲染不再等 GPU | 地图不再闪（画质随之拉满） |
| r221 | 提交改异步：回放线程是有序任务队列 | （为后续铺路） |
| r223 | 常量缓冲按字面下标读取范围原地绑定，不再复制 | 15 → 36–42 fps |
| r226 | 渲染目标切换处分批提交，GPU 与回放并行；无绑定句柄从记录读 | 24.7 → 29 fps（最重视角） |
| r227 | 管线 / 深度状态 / 着色器查询改 C 键表；调试分组可选 | 29 → 35–37 fps |
| r228 | 打开 TBDR 读写规划（可证明的 Clear / DontCare） | 35–37 → 44–48 fps |
| r232–233 | 关掉每帧 130 行日志；命令记录不再 malloc；视图跨帧缓存 | → 51 fps，瓶颈转到 GPU |
| r235 | 动态下标常量读取按绑定大小表自查越界，不再复制 | → 60 fps（GPU 约 10.7 ms/帧） |

### 7.3 可迁移的优化套路

- **把"每次都做"变成"变了才做"**：页保护脏页、按内容缓存常量缓冲、跨帧缓存视图。
- **把"复制一份保证安全"变成"证明不需要"**：常量缓冲越界读，先在构建时证明读取范围（字面下标），再把动态下标的边界检查放进着色器，彻底消掉拷贝。
- **让生产者和消费者并行**：异步提交、分批提交给 GPU。
- **去掉同步点**：能在 CPU 侧算出来的结果（已知的报告值、刚写入的常量）就不要等 GPU。
- **热路径不碰 Objective-C 对象和字符串**：描述对象、NSData 键、NSString 标签、`getenv`、`malloc`，每帧上万次累积起来就是好几毫秒。
- **TBDR GPU 上最贵的是整屏读回、写回**：减少渲染通道打断（拷贝、清除、常量更新都会打断），能用 Clear / DontCare 就用。
- **日志也是性能成本**：默认只记录关键事件，详细追踪用开关打开，且在关闭时连格式化都不要做。

## 8. 流程与协作上的教训

- **存档先备份**：每次改存档、换签名、迁移 App 前，把存档、用户 ID 文件完整拷到 `work/save-backup/<时间>/`。
- **安装失败不自动卸载**：卸载会删掉 App 的 Documents（包括存档和 3.5 GB 游戏数据）。
- **启动参数是轮次的一部分**：漏传 `WONDER_ENVS` 曾让采集模式悄悄失效。把"每轮必须带的参数"写进脚本默认值或备忘，不要靠记忆。
- **多个会话不要同时动同一台设备和同一个工作目录**：本项目出现过分支会话往手机装了旧版本、把另一个会话未提交的修改一起提交、并发构建抢同一个暂存目录导致拷贝失败。并行工作要用独立工作树，装机只由一个会话负责。
- **XML 注释里不能有 `--`**：Info.plist 改成手写文件后，注释里的 `--stage` 让构建失败。小格式规则也会卡住流水线。
- **Xcode 模块化头文件会引入同名类型**：`os/lock.h` 间接引入系统的 `struct entry`，和自己的结构体重名，宿主测试能过、真机构建失败。真机构建本身也是测试的一部分。
- **磁盘会被日志和截图吃满**：每轮控制台日志一两百 MB、截图几千张，定期清理旧轮次的大文件，保留普查数据和小文件。
- **文档跟着设备和决定走**：换设备（A11 → A20）后清理只适用于旧设备的文档；玩家决定不做的功能（全面屏），连代码一起删掉并写明"不做"，避免以后又被捡起来。

## 9. 移植其他游戏 / 其他平台时的检查清单

### 9.1 换一款 Switch 游戏

**可以直接复用的**：装载器、离线改写与验证工具、内核 SVC 实现、离线主机的系统服务、存档事务、RomFS 归档、NVN 对象与命令录制框架、NVN→Metal 回放、着色器翻译链路（翻译器 + spirv-cross + 反射）、普查与采集模式、性能计时与诊断开关、真机轮次脚本。

**必须按新游戏重新做的**：

- [ ] 输入核验：Title ID、版本、模块哈希；不复用旧游戏的哈希、地址、数据表。
- [ ] 重新盘点：引用了哪些 NVN 函数、哪些系统服务、哪些 SVC（盘点工具覆盖所有取址方式）。
- [ ] 按新游戏的 SDK 版本核对对象布局、线程布局、句柄表偏移（不同 SDK 版本可能不同）。
- [ ] 着色器：重新离线提取全部容器，重新普查；着色器键覆盖控制段 + 代码。
- [ ] 资源格式：该游戏特有的容器（如本项目的 sharcb、esetb、blarc）。
- [ ] 内存：堆大小、地址区域大小按该游戏需求。
- [ ] 字体：统计该游戏文本用到的私用区码位。
- [ ] 游戏特有的硬件语义依赖：是否依赖 GPU 计时（动态分辨率）、条件渲染、查询计数器（本项目只实现了时间戳）。

### 9.2 换一个目标平台（如 Android / Vulkan、macOS / Metal）

- **CPU 层**：目标若是 ARM64，原生执行路线仍然成立；若平台允许 JIT 或可执行内存，改写和签名环节可以简化。x86 目标则需要二进制翻译，整体路线要重新评估。
- **系统服务层**：与目标平台无关的部分（离线主机语义、存档事务、RomFS）可直接复用，只换 I/O 和音频输出后端。
- **图形层**：NVN 录制与状态跟踪可以复用，回放后端要重写（Metal → Vulkan）。着色器链路改为输出 SPIR-V 直接用，省掉 spirv-cross 到 MSL 这一步；但常量缓冲越界、顶点流越界这类语义，要按 Vulkan 的 robustness 特性重新确认。
- **平台限制先查清**：后台能否继续 GPU 工作、内存上限、地址空间大小、签名与权限、热管理。

### 9.3 通用的推进节奏

1. 先让程序"停在明确的地方"，再让它"走得更远"；
2. 先跑通启动链（引导 → 服务 → 图形初始化 → 首个绘制），不急着做性能；
3. 首帧之后用采集模式批量收集着色器，再逐个场景修画面；
4. 可玩之后再系统地做性能，每一步都有测量；
5. 长尾问题靠更好的现场信息解决，而不是靠多猜。

## 10. 本项目当前的已知问题

截至 2026-10-18（详见 [STATUS.md](../STATUS.md)）：

- **发热降频**：长时间满载后 GPU 降频，最重的地图视角从 60 fps 掉到 45–50 fps。可做的方向：继续减少渲染通道打断（常量缓冲更新打断约占 GPU 15%）；或者把真实 GPU 耗时交给游戏，让它的动态分辨率生效。
- **19 个着色器无法离线构建**：都来自引擎通用图形库；遇到时采集模式会自动记录。其中第 5 世界一个光点特效已定位，玩家决定暂不按推测值补。
- **可能遇到的停止**：模板测试、遮挡查询、多重采样、清除贴图、贴图拷到缓冲等尚未实现，遇到会按名停止。
- **后台放太久可能被系统回收**：游戏常驻内存约 1.4 GB，无法在后台释放。
- **不做的**：全面屏（画面固定 16:9）。
- **收尾**：采集模式仍开着，日志量还可以再降。
